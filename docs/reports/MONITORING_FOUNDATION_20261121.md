# Приоритетный мониторинг — рабочая версия 21.11.2026

## Состояние поставки

На CUDY остаётся принятый source 62b5c4a. Следующие функции разрабатываются в
ветке codex/monitoring-first-20261121 и ещё не установлены. WAN для переезда
отложен по просьбе владельца; его перепроектирование не блокирует мониторинг.

## Реализованные части кандидата

- Существующие два процесса сохраняются. Notifications worker измеряет состояние
  независимо от enabled/mute/categories отправителя по монотонному интервалу 60 с.
- Бюджеты recovery/наблюдения/отправки: 3/36/15 с. Отправка запускается только
  если её полный слот помещается до следующего измерения; один элемент за слот.
  Ограничиваются группы дочерних процессов, включая отказ завершиться по TERM.
- Samples содержат boot/incarnation/sequence, время работы роутера, срок свежести
  и хеш контекста. Повтор кэша не голосует заново; UNKNOWN обрывает pending,
  но не закрывает открытый инцидент. Пороги: 3 ошибки / 2 успешных результата.
- В фоне приоритет имеют WAN IPv4 direct, DNS, MAIN и профиль REDMI. WAN и MAIN
  имеют сокращённые внешние deadlines; Torrent не запускает дополнительную
  внешнюю пару запросов. Локальные отказы
  Torrent остаются видны; положительный внешний кэш не используется фоновым
  циклом и внешний результат остаётся UNKNOWN. Интерактивная проверка сохранена.
- История: 7 суток подробных интервалов и 30 дневных агрегатов, checkpoint
  каждые 15 минут; стабильные интервалы сжимаются. Лимит подробного снимка вместе
  с агрегатами 2 MiB, агрегатов 512 KiB. При сокращении полнота явно отмечена.
  Это лимиты файла, а не утверждение о расходе RAM на CUDY.
- /summary и кнопка «За сутки», /history и «За неделю» читают сохранённую историю
  без новых проб. Покрытие, UNKNOWN и отсутствие наблюдений показаны отдельно.
  Последний результат не продлевается до текущего времени без новых измерений.
- `gateway notifications configure monitoring` включает четыре категории и
  сохраняет действующие mute и паузу Telegram 429. Автоматические напоминания,
  STATE_CHANGED и прочие категории не отправляются минутным worker.

## Обновление и ограничения

V3 — явный формат HG_OWNER_MONITOR_V3 с непосредственным baseline 62b5c4a
и V2 parent. Runtime inventory остаётся 20 путей, control inventory 14;
разрешены только восемь существующих файлов. Старые V1/V2 ограничения не сняты.
Функциональный setsid проверяется до записей; откат остаётся доступен без него.

Срок 2–4 минуты — цель при доступном Telegram, не измеренная гарантия CUDY.
Часы помечаются неподтверждёнными без отдельного доказательства; интервалы
считаются по uptime. DNS REDMI не доказывает интернет телефона. Откат runtime
не перематывает историю и очередь. Доставка Telegram сохраняет at-least-once
ограничение при потере квитанции; ID позволяет распознать возможный повтор.

## До готового установщика

1. Завершить общие regression tests и независимую проверку изменений.
2. Пройти native OpenWrt V3 apply/verify/rollback, crash cuts и reboot;
   затем exact-source GitHub CI. Промежуточный VM snapshot не заменяет эти gates.
3. No-install readiness владельца выполнен: результат приведён ниже.
   Агент к рабочему роутеру не подключается.
4. Подготовить owner-пакет и ручные Preflight → Apply → отдельный Verify;
   включить согласованный preset уведомлений после успешного Verify.
5. Проверить Telegram и клиентов, затем 24–72 часа естественного наблюдения.

## Совместимость состояния после отката

Ограничение baseline62: incident_id должен соответствовать component-[0-9]+.
Новые ID сохраняют эту грамматику: boot/incarnation losslessly кодируются
фиксированными десятичными парами плюс sequence. Полный ID хранится без
сокращения; в Telegram показан компактный код для распознавания повторов.

Regression test исполняет точные incidents.uc/notifications.uc baseline62
(проверены SHA256) на очереди и журнале новой версии: чтение, compaction,
завершение нового инцидента старым кодом и последующее чтение новым кодом.
Это дополняет native rollback runtime; история/очередь не перематываются назад.
Первоначальный UUID-формат был несовместим и исправлен до публикации пакета.

Дополнительные fault tests: отказ checkpoint истории после сохранения фактов
не блокирует доставку (exit75 / HISTORY_DEGRADED); потерянный цикл сбрасывает
pending и отмечает пропуск истории, а replay того же frame игнорируется.
Наблюдение, подтверждение инцидента, хранение и отправка остаются раздельными.

В native crash harness исправлена проверка устаревшей квитанции baseline после
появления новых завершённых операций. Теперь проверяется последняя квитанция,
а возврат runtime к baseline отдельно подтверждается хешами всех его файлов.
Защита HISTORY_GENERATIONS не менялась. Полный локальный CI на7372e63 прошёл;
финальная приёмка native/CI для поставляемого source ещё выполняется.
