## Зафиксированные требования

| Область | Решение владельца |
|---|---|
| Интерфейс и размещение | Telegram, всё на CUDY, без web UI и внешнего наблюдателя |
| Автоматические сообщения | WAN, DNS, MAIN VPN и профиль REDMI; круглосуточно |
| Частота сообщений | Один раз о подтверждённом сбое и один раз о восстановлении; без напоминаний |
| Полный обрыв | Отчёт после восстановления; выключение питания оставляет неизвестный промежуток |
| Задержка | Цель 2–4 минуты при доступном Telegram; ещё требует проверки |
| REDMI | Профиль проверяется всегда, отсутствие телефона не ошибка; смена локации в PassWall2 |
| История | 7 суток подробно, 30 суток дневных сводок, с явным признаком неполноты при ограничении размера |
| Запись во flash | Допустима потеря до 15 минут несохранённых подробностей; подтверждённые события сохраняются отдельно |
| Сводки | Только по запросу, без автоматического дневного отчёта |
| Переезд | Новый провайдер или вышестоящий роутер, прежний физический WAN-порт CUDY |

Torrent, ASATA и Tailscale остаются в состоянии и истории, но без автоматических
тревог первого выпуска. Это фильтр доставки, а не отключение наблюдения.

## 0. Основание и подготовка к переезду

**Результат:** отдельная памятка переноса и проверяемые ограничения будущего
мониторинга. Этот этап можно закончить до изменения работающего роутера.

- Зафиксировать исходные версии, работоспособность Telegram и клиентов;
  определить безопасный способ получения времени проверок и расхода ресурсов.
- Подготовить инструкцию владельцу: приватная резервная копия конфигурации OpenWrt,
  проверка её состава, доступности и способа локального восстановления. Архив
  текущего установщика содержит runtime проекта и не заменяет эту копию.
- Составить карточку подключения: DHCP/static/PPPoE, VLAN, привязка MAC,
  подсеть вышестоящего роутера. Неизвестные параметры заполняются перед переездом;
  пароли и реальные архивы не попадают в Git или переписку.
- Проверить сценарий совпадения подсетей нового роутера и LAN CUDY. Показывать
  предупреждение и порядок ручного исправления, без автоматической смены LAN.
- На стенде проверить DNS-клиент, нестандартный порт, общий timeout; рассчитать
  полный цикл наблюдения вместе с медленным Telegram, fallback и очередью.
  Отдельно измерить бюджет RAM, flash и временного места для записи истории.

**Критерий завершения:** памятка не требует заранее тянуть резервный LAN-кабель;
он остаётся аварийным вариантом. Для DNS и расписания есть воспроизводимые
результаты и решение о допустимых интервалах. Ни 60 секунд опроса, ни 8 MiB
истории пока не выдаются за измеренные возможности CUDY.

## 1. Достоверная диагностика REDMI

**Результат:** бот различает наличие профиля, процесса, правил, Kill Switch и
ответ DNS именно действующего профиля. Проверка выполняется и без телефона.

Обнаруживать актуальный endpoint, привязывать результат к профилю/порту/узлу,
показывать возраст и область проверки. Смена локации через PassWall2 делает
старые данные неприменимыми и начинает новую серию подтверждения. Название
настроенного узла не выдаётся за доказательство фактически выбранного выхода.
DNS-успех не называется проверкой интернета на REDMI.

**Проверки:** профиль отсутствует, порт изменился, DNS завис, ответ некорректен,
старый кэш, смена узла во время запроса, телефон отключён. Последнее само по
себе не создаёт сбой. Telegram не переключает локацию.

**Зависимость поставки:** узкий DNS/freshness-пакет возможен только в пределах
пяти разрешённых файлов нынешнего установщика. Если проверенный DNS-инструмент
или контракт требует большего scope, сначала этап 2; ограничения не обходятся.

## 2. Расширенный путь обновления

**Результат:** проверенный установщик для согласованного набора изменений
сетевого адаптера, инцидентов, доставки, CLI и истории.

Текущий установщик рассчитан на пять observer/UI-файлов и фиксированные
20 runtime paths. Перед расширением отдельно определить новый inventory,
проверки допустимости, создание/удаление новых файлов при восстановлении,
совместимость старых подтверждений и сохранённых данных. Новый модуль не
добавляется незаметно двадцать первым файлом.

**Проверки:** несовпадение исходной версии, частичная установка, перезапуск,
откат с актуальной очередью и чтение нового состояния старой версией. Если
совместимость невозможна, сначала промежуточный совместимый выпуск. Откат
кода не перематывает пользовательскую историю и очередь назад.

## 3. Готовность WAN к смене подключения

**Результат:** диагностика нового WAN через прежний порт без зависимости от
старых адресов и провайдера. Памятка этапа 0 доступна раньше этого выпуска.

Использовать фактический интерфейс из состояния OpenWrt; различать линк,
адрес, маршрут, DNS и внешний direct-выход. Проверить DHCP, static и PPPoE
на стенде; маршруты без обычного `via` и IPv6 показывать согласно реально
поддержанному scope. Неизвестный протокол не объявлять рабочим по наличию линка.

При изменении подключения отделять результаты новой сети от старой, сбрасывать
неприменимый внешний кэш и серии подтверждения. Переезд — граница контекста,
а не автоматическое «восстановление старого провайдера».

**Приёмка переноса владельцем:** доступ к CUDY → WAN/маршрут → DNS и время →
MAIN VPN → Telegram → интернет на компьютере и REDMI. Новые настройки вводятся
владельцем по данным провайдера. Автоматическое изменение WAN из Telegram
в этот план не входит. Рабочее сетевое подключение не ломаем ради теста.

## 4. Независимое наблюдение и ранняя история

**Результат:** выключение сообщений не прекращает проверки; история начинает
накапливаться до появления экрана статистики.

Разделить измерение, инцидент и доставку. Использовать новые независимые samples,
3 неуспеха для подтверждения и 2 успеха для восстановления. Повтор одного кэша
не голосует снова; UNKNOWN разрывает ожидающую серию и не закрывает открытый
инцидент. Рестарт, смена профиля/сети и неподтверждённые часы явно видны.

Начальный вариант — существующие два процесса с ограниченными задачами.
При непрохождении бюджета отдельный сборщик требует пересмотра запуска и
поставки до выпуска. Медленная отправка не может вытеснить очередную проверку.

**Проверки:** Telegram завис/429/backlog, OFF/mute, повтор кэша, сбой процесса,
reboot, смена сети, скачок часов. Измерить всю цепочку для цели 2–4 минуты;
если цель не достигнута, исправить расписание или явно пересмотреть проект.

## 5. Полезные сообщения без потока повторов

**Результат:** четыре выбранных направления сообщают о сбое и восстановлении
24/7. Нет периодических напоминаний, тихих часов и автоматической сводки.

Объединять связанные последствия WAN только по свежим фактам, сохраняя каждое
наблюдение. Ошибку Kill Switch не прятать за общей проблемой сети. Если Telegram
был недоступен весь инцидент, после восстановления отправлять понятный отчёт,
а не шквал устаревших тревог. Указывать время наблюдения и задержку доставки.
Сохранять текущие транспортные ограничения и обработку `retry_after`.

**Проверки:** один сбой/одно recovery, несколько независимых сбоев, завершённый
инцидент без связи, пропавшее подтверждение Telegram, заполнение очереди,
пауза/возобновление. Потерянный ACK может дать повтор с тем же ID; абсолютная
однократность доставки не обещается. Аварии воспроизводятся на стенде.

## 6. Telegram: состояние, REDMI и история по запросу

**Результат:** короткая главная, причины проблемы REDMI и история за сутки/неделю.
«Обновить экран» читает снимок, «Проверить сейчас» запускает ограниченную задачу
с объединением повторных нажатий. Во время длинной проверки есть быстрый ответ.

Диагностика REDMI показывает проверенные факты, неизвестное и следующий ручной
шаг в PassWall2. Сводка выводит наблюдаемую доступность вместе с покрытием:
пропуски, питание и обслуживание не считаются успешным интернетом. Это не
измеритель скорости или доказательство доступности всех сайтов на телефоне.

Хранить целевые 7/30 суток в ограниченном объёме; checkpoint не реже выбранных
15 минут, события отдельно при переходе. При нехватке места помечать историю
неполной, не удалять активные инциденты и неотправленную очередь ради статистики.
Проверить объём записи и запас для атомарного сохранения до выпуска.

**Проверки:** нет данных/неполный день, граница суток и перезапуск, повреждённая
запись, ограничение размера, старые кнопки, чужой пользователь, повторный callback.
Read-only навигация не получает права изменения настроек.

## Порядок выпуска и документация

Последовательность: **0 → 1 (если позволяет узкий scope) → 2 → 3 → 4 → 5 → 6**.
История начинает записываться на этапе 4; её пользовательский экран — на этапе 6.
Перенос WAN не обязан ждать всей программы: памятка выпускается на этапе 0,
сетевая диагностика имеет отдельную приёмку на этапе 3.

Каждый runtime-выпуск: подходящие компонентные и аварийные тесты, независимая
проверка, действующие CI/native gates, затем ручные Preflight → Apply → отдельный
Verify владельца и проверки клиентов. После принятого этапа — наблюдение
24–72 часа без искусственных аварий на рабочем CUDY. При регрессии дальнейшие
выпуски останавливаются; восстановление выполняется проверенным для пакета путём.

В каждом выпуске обновлять руководство, ограничения, примеры сообщений и
чек-лист приёмки. Имеющиеся схемы и настоящий пример Gatus сохраняются с
подписями; реальные скриншоты CUDY добавлять после приёмки соответствующих
экранов, скрывая секреты. Концепты не переименовываются в скриншоты продукта.

Это программа работ. Перед кодом каждого независимого выпуска нужен его
короткий инженерный план с точными файлами, интерфейсами и тестами; особенно
для расширенного установщика. Неизвестные параметры нового провайдера не
мешают начать подготовку и понадобятся непосредственно перед переносом.
